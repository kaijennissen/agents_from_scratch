# Diary

Append-only log of pitfalls encountered and decisions made while building the agent, newest at the bottom. One entry per topic per day.

30.07.2026 10:09 subprocess(cmd, shell=True), Tags: subprocess, shell, tool; Without `shell=True`, the first argument is the program to run — not a command line.
  - Pass a list: run(["find", ".", "-name", "agent.py"]) → Python executes the program `find` directly with those args. No shell.
  - Pass a string: run("find . -name agent.py") → Python treats the entire string as the program name, so it looks for an executable literally called `find . -name "agent.py" ...` → FileNotFoundError.

  What `shell=True` adds: it runs your string as `/bin/sh -c "your string"`, so a real shell parses it — giving word-splitting, glob expansion (`*.py`), pipes (`|`), `&&`, and redirections like `2>/dev/null` (which the program itself never sees). Caveat: `shell=True` on model-written commands is shell injection by design → the process boundary (container/sandbox), not argv safety, is the real protection.

  `sh -c` contract: the command is the ONE string right after `-c`; tokens after that become positional params ($0, $1, …). So `["/bin/sh","-c"] + shlex.split(cmd)` runs only the first token (`find`) with no args — don't pre-split. And `["/bin/sh","-c", cmd]` is exactly what `shell=True` does internally, so hand-rolling it buys no safety. Decision: use `shell=True` with the raw model string (less code, nothing to hand-add). Safety reasoning: the model authors the whole command, so argv-vs-shell is the wrong layer — real safety is the boundary (non-root container, no secrets reachable, no egress) plus a per-command `timeout`.

30.07.2026 12:21 re.DOTALL, Tags: regex, parsing; Without `re.DOTALL`, `.` matches everything except newlines. In `parse_xml` the pattern `<tag>(.*?)</tag>` needs `re.DOTALL` so that content spanning multiple lines (e.g. a multi-line `<bash>` command) is captured — otherwise the match stops at the first `\n` inside the tag.

30.07.2026 12:21 SYSTEM_PROMPT never sent to model, Tags: system-prompt, messages, bug; Defined `SYSTEM_PROMPT` but never included it in `messages` — the model received only the user's question with no instructions, so it answered generically instead of emitting `<action>` tags. Fix: add `{"role":"system","content":SYSTEM_PROMPT}` as the first element of `messages`. Lesson: defining a prompt ≠ wiring it into the call.

30.07.2026 12:21 `*` can't flatten inside a comprehension, Tags: python, itertools, unpacking; `[*sub for sub in lists]` is a syntax error — `*` unpacks into an enclosing literal or call, not inside a comprehension. To flatten one level of nesting: `itertools.chain.from_iterable(lists)` or a nested comprehension `[x for sub in lists for x in sub]`. Decision: used `itertools.chain.from_iterable` in `parse_action`.

30.07.2026 12:21 2>/dev/null, Tags: shell, redirection; `2` = stderr (fd 2; 0=stdin, 1=stdout), `>` = redirect that stream, `/dev/null` = discard. So `2>/dev/null` throws away error output, keeps stdout. Related: `>/dev/null 2>&1` discards both; `2>&1` merges stderr into stdout (one stream).

30.07.2026 12:21 CompletedProcess not JSON serializable, Tags: subprocess, json, serialization; Appending the raw `subprocess.run(...)` result to `messages` → TypeError because `CompletedProcess` isn't JSON-serializable. Fix: extract `result.stdout`/`result.stderr` (strings) and build `content` from those. Also: without `text=True`, stdout/stderr are `bytes` not `str` → second serialization error waiting to happen.

30.07.2026 12:21 One-action-per-turn (for now), Tags: design, loop, actions; Decision: keep one action per turn. The loop is act→observe→decide — batching bash commands means committing to commands 2–N blind, before seeing command 1's output. Add bash-batching only when a real run shows wasted round-trips on independent commands. `parse_action` already returns lists per kind, so the structure is ready for multiplicity.

30.07.2026 14:05 lists-per-kind was the wrong shape, Tags: design, parsing, types, revision; Reversing the "ready for multiplicity" note above. Bucketing every tag into three lists cost ~15 lines of `itertools.chain.from_iterable` to support a case the system prompt explicitly forbids ("exactly one action"), and it hid a real bug: three lists mean the caller must pick a precedence, and `actions.get("exit", None)` on a TypedDict reads as optional when the key can never be missing — `.get` always hands back a list. Now `parse_action` returns `dict[str, str]` for the single action found (first of `("exit", "bash")` wins, so exit beats bash), `{}` when unparseable, and `if "exit" in action` carries the meaning. Lesson: modelling what the prompt *permits* beats modelling what the model *might* send — speculative generality in a learning project is just ceremony, and the ceremony is where the bugs hide.

30.07.2026 14:05 dead loop-control variables, Tags: python, loop, bug; `stop` was initialized `False` and never assigned, so `while not stop:` was `while True:` wearing a disguise. Same shape: `turn += 1` followed by `if turn > max_turns: break` reimplements `for`. A variable that is never mutated is not state, it is decoration — and a reader must trace every assignment to learn it does nothing. Replaced with `for _ in range(MAX_TURNS)`. Both the top-of-loop (`turn > max_turns`) and bottom-of-loop (`turn >= max_turns`) forms yield the same 5 calls, so "move the increment" was never the fix; removing the counter was.

30.07.2026 14:05 exit answer was thrown away, Tags: bug, output, design; The loop found a non-empty `<exit>` action and then `break`ed without keeping the body — the agent discarded its own result and exited silently, every time. `<exit>` is the *only* channel the final answer travels through, so returning it is the feature, not a print. `main()` now returns `str` and `cli()` prints it; returning rather than printing keeps the loop testable without capturing stdout. Corollary for the removed `<message>`: in a one-shot CLI nobody is reading mid-loop prose, and it was never even appended to `messages` — dropped from prompt, parser, and loop. It comes back with a session loop wrapped *around* the while-loop, where a user can actually answer.

30.07.2026 14:05 f-string indentation leaks into context, Tags: python, f-string, context; A triple-quoted f-string in an indented block carries its own source indentation into the string, so every observation reached the model padded with ~12 spaces of leading whitespace. Cost is tokens and a subtly malformed block, not a crash — the quietest kind of bug. Fix: build observations with `"\n".join([...])`. Note this only became visible once the f-string was the thing being sent to a model; nothing about the code failed, which is exactly why eyeballing the *rendered* prompt matters.

30.07.2026 14:05 the turn counter cannot save you from a hang, Tags: subprocess, timeout, robustness; `MAX_TURNS` bounds the loop, but `subprocess.run` with no `timeout` blocks *inside* an iteration — one `sleep 999` and the budget never gets a chance to be checked. Wall-clock limits have to attach to the tool call, not (only) to the loop around it. Same call, same lesson as output truncation: every turn re-sends the whole transcript, so unbounded stdout is context you pay for on all remaining turns. Added `timeout=120` and `MAX_OUTPUT_CHARS = 2000`.

30.07.2026 14:12 capture_output=True and stderr=STDOUT are mutually exclusive, Tags: subprocess, api, pitfall; Wanted both streams in one capture (`stderr=subprocess.STDOUT` is the programmatic `2>&1`) and got `ValueError: stdout and stderr arguments may not be used with capture_output.` `capture_output=True` is just sugar for `stdout=PIPE, stderr=PIPE`, so the moment you spell `stderr` out yourself the sugar conflicts with it. Drop `capture_output=True` and write `stdout=subprocess.PIPE, stderr=subprocess.STDOUT` — same result, and now visible in the source why there is only one stream to read.

30.07.2026 14:12 helpers hide the thing you are teaching, Tags: design, readability, learning-project; Wrapping the bash call in `run_bash()` returned a tidy observation string, but it put three steps (run, format, append) behind one call inside a file whose entire job is to *show* those three steps. The observation is a f-string, not an abstraction: it is cheaper to read inline than to name. Rule of thumb for this repo — extract a function when the logic is worth testing in isolation (`parse_action`), keep it inline when the inline version is already the clearest statement of what happens (`subprocess.run` → append). The append is now literally one line, which is the point of the loop.
